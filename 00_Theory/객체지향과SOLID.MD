# 절차 지향, 객체 지향, SOLID

## 객체란?

**객체(object)** 는 프로그램 안에서 어떤 대상을 표현한 실제 값입니다. 객체는 자신이 기억해야 할 **데이터(상태)** 와 자신이 할 수 있는 **기능(행동)** 을 함께 가집니다.

게임을 예로 들면 `Player`, `Monster`, `Item`, `Inventory`를 각각 객체로 생각할 수 있습니다.

```text
Player 객체    : 이름, 체력, 골드 / 공격한다, 아이템을 사용한다
Monster 객체   : 이름, 체력, 공격력 / 플레이어를 공격한다, 피해를 받는다
Item 객체      : 이름, 가격, 회복량 / 사용된다
Inventory 객체 : 아이템 목록 / 아이템을 추가한다, 아이템을 꺼낸다
```

클래스는 객체를 만들기 위한 설계도이고, 클래스로 실제 값을 만들면 객체가 됩니다.

```cpp
Player player; // Player라는 설계도로 만든 실제 객체
Monster slime; // Monster라는 설계도로 만든 실제 객체
```

## 객체 지향이란?

**객체 지향 프로그래밍(Object-Oriented Programming)** 은 프로그램을 하나의 거대한 처리 절차로만 보지 않고, **각자 데이터와 기능을 가진 객체들이 서로 요청하고 협력하는 프로그램**으로 만드는 방식입니다.

예를 들어 플레이어가 슬라임을 공격할 때, `main()` 함수가 체력 계산을 전부 직접 처리하는 대신 다음처럼 객체에게 일을 요청할 수 있습니다.

```cpp
player.Attack(slime); // Player 객체가 공격을 요청합니다.
slime.TakeDamage(10); // Monster 객체가 자신의 체력 감소를 처리합니다.
```

각 객체는 자기 상태를 관리하고 자기 역할에 맞는 일을 담당합니다. 따라서 “누가 이 일을 맡아야 하지?”를 먼저 생각하는 것이 객체 지향 설계의 출발점입니다.

## 프로그램을 구성하는 두 관점

프로그램은 같은 기능을 여러 방식으로 설계할 수 있습니다. **절차 지향 프로그래밍**은 “어떤 순서로 처리할 것인가”에 초점을 두고, **객체 지향 프로그래밍**은 “어떤 객체가 어떤 데이터와 책임을 가질 것인가”에 초점을 둡니다.

둘 중 하나가 항상 더 좋은 것은 아닙니다. 작은 계산, 간단한 알고리즘, 한 번만 처리하는 작업은 절차 지향 방식이 명료할 수 있습니다. 반대로 게임처럼 플레이어·몬스터·아이템처럼 서로 다른 대상이 오래 상호작용하고 기능이 늘어나는 프로그램은 객체 지향 방식이 구조를 관리하는 데 도움을 줍니다.

| 관점 | 절차 지향 | 객체 지향 |
| --- | --- | --- |
| 중심 | 처리 순서와 함수 | 객체의 데이터, 기능, 책임 |
| 코드 구성 | 데이터와 함수가 비교적 분리됨 | 관련 데이터와 기능을 클래스로 묶음 |
| 생각하는 질문 | “다음에 무엇을 할까?” | “어떤 객체가 이 일을 맡아야 할까?” |
| 잘 맞는 예 | 별 찍기, 배열 탐색, 간단한 계산 | 게임 캐릭터, 인벤토리, UI, 여러 상태를 가진 시스템 |

## 절차 지향의 예

아래 코드는 플레이어의 데이터를 별도 변수로 두고, 함수를 호출해 처리합니다. 흐름을 위에서 아래로 따라가기 쉬운 방식입니다.

```cpp
int playerHp = 100;

void TakeDamage(int& hp, int damage)
{
    hp -= damage;
    if (hp < 0)
    {
        hp = 0;
    }
}

TakeDamage(playerHp, 30);
```

플레이어가 하나이고 기능이 적을 때는 충분히 좋은 코드입니다. 다만 이름, 체력, 레벨, 장비, 스킬을 가진 플레이어와 몬스터가 여러 종류로 늘어나면, 어느 함수가 어느 데이터와 관련 있는지 찾는 일이 점점 어려워질 수 있습니다.

## 객체 지향의 예

객체 지향에서는 플레이어의 데이터와 플레이어가 할 수 있는 일을 `Player` 클래스 안에 둡니다. 그리고 다른 객체는 `Player`에게 필요한 일을 요청합니다.

```cpp
class Player
{
private:
    int mHp = 100;

public:
    void TakeDamage(int damage)
    {
        mHp -= damage;
        if (mHp < 0)
        {
            mHp = 0;
        }
    }
};
```

이제 체력을 바꾸는 규칙은 `Player` 객체가 담당합니다. 다른 객체나 외부 코드는 `player.TakeDamage(30);`처럼 **무엇을 원하는지**만 요청하고, 체력을 어떻게 0 이상으로 유지할지는 `Player`가 책임집니다. 객체들이 각자 맡은 역할을 처리하며 상호작용하는 구조입니다.

## 객체 지향의 핵심 요소

### 1. 캡슐화(Encapsulation)

관련된 데이터와 기능을 하나의 클래스에 묶고, 내부 구현을 필요한 만큼 감추는 것입니다.

- `private` 멤버 변수로 중요한 데이터를 보호합니다.
- `public` 멤버 함수로 안전한 사용 방법을 제공합니다.
- 잘못된 상태가 만들어지는 것을 막습니다. 예: 체력은 0 아래로 내려가지 않게 합니다.

캡슐화의 목적은 “무조건 숨기기”가 아닙니다. 객체를 사용하는 사람이 꼭 알아야 할 사용 방법은 공개하고, 내부에서 바뀔 수 있는 구현 세부 사항은 감춰 변경의 영향을 줄이는 것입니다.

### 2. 추상화(Abstraction)

복잡한 내부 과정 중 사용에 꼭 필요한 핵심만 보여 주고, 나머지는 감추는 것입니다.

자동차 운전자는 엔진의 모든 내부 구조를 알지 않아도 핸들, 브레이크, 가속 페달로 자동차를 운전합니다. 마찬가지로 게임 코드에서는 `player.Attack();`를 호출하는 쪽이 피해 계산식 전체를 알 필요가 없게 만들 수 있습니다.

추상 클래스와 순수 가상 함수는 “이 기능이 있어야 한다”는 공통 규칙을 표현하는 대표적인 도구입니다.

### 3. 상속(Inheritance)

공통 특징을 가진 클래스를 기반 클래스로 만들고, 더 구체적인 클래스가 이를 물려받는 것입니다.

```cpp
class Character { /* 이름, 체력 등 공통 요소 */ };
class Warrior : public Character { /* 전사만의 요소 */ };
class Wizard : public Character { /* 마법사만의 요소 */ };
```

상속은 코드 재사용과 계층 표현에 유용하지만, “재사용하고 싶다”는 이유만으로 사용하는 도구는 아닙니다. `Warrior`가 `Character`라고 말할 수 있는 **is-a 관계**일 때 자연스럽습니다.

### 4. 다형성(Polymorphism)

같은 호출 방식이 실제 객체에 따라 다르게 동작하는 성질입니다.

- **정적 다형성**: 컴파일할 때 결정됩니다. 함수 오버로딩, 템플릿 등이 예입니다.
- **동적 다형성**: 실행 중 실제 객체의 타입에 따라 결정됩니다. 상속과 가상 함수가 예입니다.

```cpp
Character* character = &warrior;
character->Attack(); // virtual 함수라면 Warrior의 Attack이 호출됩니다.
```

새 직업을 추가할 때 기존의 긴 `if` 또는 `switch` 문을 계속 수정하는 대신, 각 직업이 `Attack()`을 구현하게 할 수 있습니다. 이것이 다형성이 주는 확장성입니다.

> 클래스와 객체는 도구이고, 캡슐화·추상화·상속·다형성은 코드를 나누어 생각하는 방법입니다. 네 요소를 모든 클래스에 억지로 넣을 필요는 없습니다.

## SOLID 원칙이란?

**SOLID**는 클래스와 객체를 협력하게 설계할 때 자주 참고하는 다섯 가지 원칙의 앞글자입니다. 정답을 자동으로 만들어 주는 규칙이 아니라, 코드가 커질 때 결합도를 낮추고 변경하기 쉽게 만드는 **설계 점검 기준**입니다.

처음부터 모든 원칙을 완벽하게 적용하려고 하면 오히려 코드가 복잡해질 수 있습니다. 우선 각 원칙이 어떤 문제를 막으려는지 이해하고, 중복과 수정이 불편해질 때 적용합니다.

### S — 단일 책임 원칙 (Single Responsibility Principle)

**클래스는 변경되는 이유가 하나여야 한다**는 원칙입니다.

`Player`가 플레이어 상태를 관리하면서 파일 저장, 화면 출력, 네트워크 전송까지 전부 담당하면, 저장 형식이나 UI가 바뀌어도 `Player` 클래스를 수정해야 합니다. 역할을 나누면 변경 범위가 작아집니다.

```text
Player        : 플레이어 상태와 게임 규칙
PlayerPrinter : 플레이어 정보를 화면에 출력
PlayerSaver   : 플레이어 정보를 파일에 저장
```

### O — 개방-폐쇄 원칙 (Open/Closed Principle)

**확장에는 열려 있고, 기존 코드 수정에는 닫혀 있게** 설계한다는 목표입니다.

새로운 몬스터를 추가할 때 기존 몬스터 처리 코드를 계속 고치는 대신, 공통 기반 클래스의 가상 함수를 새 몬스터가 `override`하도록 만들 수 있습니다.

```cpp
class Monster
{
public:
    virtual void Attack() const = 0;
    virtual ~Monster() = default;
};

class Goblin : public Monster
{
public:
    void Attack() const override { /* 고블린 공격 */ }
};
```

“기존 코드를 절대로 수정하지 않는다”는 뜻은 아닙니다. 변화가 예상되는 부분을 인터페이스와 다형성으로 분리해, 새 기능 추가가 기존 코드의 연쇄 수정으로 번지는 일을 줄이자는 원칙입니다.

### L — 리스코프 치환 원칙 (Liskov Substitution Principle)

**기반 클래스 자리에 파생 클래스를 넣어도 프로그램의 약속이 깨지지 않아야 한다**는 원칙입니다.

예를 들어 `Character*`를 받는 함수는 전사든 마법사든 정상적으로 처리할 수 있어야 합니다. 자식 클래스가 부모의 의미를 뒤집거나, 부모보다 훨씬 까다로운 조건을 요구하면 이 원칙을 깨뜨릴 수 있습니다.

```cpp
void ProcessAttack(const Character& character)
{
    character.Attack(); // 어떤 Character 파생 객체라도 호출 가능해야 합니다.
}
```

### I — 인터페이스 분리 원칙 (Interface Segregation Principle)

**사용하지 않는 기능을 억지로 구현하게 만들지 말라**는 원칙입니다.

`ICharacterAction`에 공격, 이동, 비행, 수영을 모두 넣으면 땅에서만 이동하는 몬스터도 비행 함수를 만들어야 합니다. 필요한 역할 단위로 나누는 편이 낫습니다.

```text
Attackable : Attack()
Movable    : Move()
Flyable    : Fly()
```

### D — 의존성 역전 원칙 (Dependency Inversion Principle)

**구체적인 클래스가 아니라 추상화(인터페이스·추상 클래스)에 의존하라**는 원칙입니다.

예를 들어 게임 진행 코드가 `Goblin`만 직접 알면 다른 몬스터를 넣을 때 코드가 바뀝니다. `Monster`라는 추상 클래스에 의존하면 고블린·슬라임·보스 몬스터를 같은 방식으로 다룰 수 있습니다.

```cpp
void UpdateMonster(const Monster& monster)
{
    monster.Attack(); // Goblin이 아니라 Monster라는 공통 약속에 의존합니다.
}
```

## 핵심 정리

- 절차 지향은 처리 순서, 객체 지향은 데이터와 책임의 주체를 중심으로 생각합니다.
- 객체 지향의 핵심 요소는 캡슐화, 추상화, 상속, 다형성입니다.
- SOLID는 역할을 적절히 나누고 변경에 강한 구조를 만들기 위한 설계 점검 기준입니다.
- 작은 예제부터 무리하게 복잡한 구조를 만들 필요는 없습니다. 코드가 커지며 “어디를 고쳐야 하지?”가 어려워질 때 원칙을 떠올립니다.

## AI 코딩·바이브 코딩 시대에 SOLID가 중요한 이유

AI를 이용하면 기능이 동작하는 코드를 매우 빠르게 만들 수 있습니다. 하지만 **“지금 실행된다”** 와 **“다음 기능을 안전하게 추가할 수 있다”** 는 서로 다른 문제입니다.

예를 들어 AI에게 몬스터를 하나 추가해 달라고 요청했을 때, 기존 코드 곳곳의 `if`, `switch`, 전역 변수까지 함께 수정하는 코드를 만들 수 있습니다. 처음에는 동작하더라도 몬스터 종류가 계속 늘어나면 수정할 위치를 놓치거나 다른 기능을 깨뜨리기 쉬워집니다.

SOLID는 AI가 만든 코드를 검토하거나 다음 요청을 작성할 때 유용한 질문을 제공합니다.

- **S**: 이 클래스가 게임 규칙, 화면 출력, 파일 저장까지 모두 맡고 있지는 않은가?
- **O**: 새 직업·몬스터를 추가할 때 기존의 여러 파일을 계속 고쳐야 하는가?
- **L**: 부모 타입으로 다루던 자리에 어떤 자식 객체를 넣어도 같은 약속이 지켜지는가?
- **I**: 이 객체가 사용하지 않는 기능까지 억지로 구현하고 있지는 않은가?
- **D**: 특정 구현체 하나에 묶여 있는가, 아니면 공통 인터페이스에 의존하는가?

따라서 AI에게는 “몬스터 클래스를 추가해 줘”보다 “`Monster` 인터페이스를 유지하고, 기존 전투 코드를 수정하지 않으며 새 몬스터 클래스를 추가해 줘”처럼 구조적 제약까지 함께 요청할 수 있습니다. AI가 작성한 코드도 이 질문으로 확인하면, 단순히 실행되는 코드를 넘어 **변경·확장·협업하기 쉬운 코드**에 가까워집니다.

> SOLID를 외워서 모든 코드에 적용하는 것이 목표는 아닙니다. AI가 제안한 구조를 그대로 받아들이지 않고, 각 객체의 책임과 의존 관계를 판단하는 기준으로 사용하는 것이 중요합니다.
